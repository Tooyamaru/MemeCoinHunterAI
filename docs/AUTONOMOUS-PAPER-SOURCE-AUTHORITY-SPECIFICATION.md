## 2. Selected discovery mechanism: one finalized block

Proposed source owner identity: `solana-finalized-mint-initialization-v1`. Chain scope is Solana mainnet under the existing trusted Solana transport configuration. A future operational binding must pin/verify the mainnet cluster identity; a vendor URL alone is insufficient. No transport or runtime binding is created here. Cluster verification is a separate prerequisite for that future binding, not an undisclosed fourth call inside discovery.

One `discover_once` invocation has exactly this dependency order, each method at most once:

1. `getSlot([{"commitment":"finalized"}])` obtains slot S.
2. `getBlock([S,{"commitment":"finalized","encoding":"jsonParsed","transactionDetails":"full","maxSupportedTransactionVersion":0,"rewards":false}])` obtains that exact block.
3. `getBlockTime([S])` obtains its ledger time. Require integer Unix seconds, convert exactly to aware UTC, and require equality with the non-null `blockTime` from step 2. The method has no commitment parameter; finality derives from steps 1/2, not a fabricated response flag.

This selects a ledger event set without a supplied token mint. It deliberately covers one block's successful mint-initialization events, not all existing tokens or a continuous discovery history. `getBlockTime` is Solana's estimated block-production clock; it is source-anchored but does not prove exact intra-block execution time or an account's last mutation time.

Programs are exactly `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` and `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb`, as already supported by the selected-mint owner. Accept only parsed `initializeMint` / `initializeMint2` instructions whose `programId` matches the supported program and whose parsed mint is a canonical case-sensitive base58 32-byte public key. Do not trust a program display name or symbol. Inspect top-level instructions and recorded inner instructions of successful transactions (`meta.err` is null), retaining their original positions. Failed transactions produce no discovery events. Reject incomplete metadata, unresolved version/address-table identity, or opaque supported-token instructions where completeness of initialization extraction cannot be established. Do not infer an initialization from a token balance change.

The event tuple is `(chain, program, S, blockhash, transaction_signature, outer_instruction_index, inner_instruction_index_or_null, mint)`. Its versioned canonical-JSON SHA-256 is the source event ID. Keep original transaction and instruction positions as lineage. A block-local traversal ordinal may be the numeric P02 cursor; it denotes only within-block source order, never a global sequence or proof that preceding slots were consumed.

`RawEvent.event_time` is the checked block time. `RawEvent.received_time`, `AdapterObservation.observed_time` and batch receipt time are the batch-completion receipt, satisfying the existing exact receipt linkage. Retain each individual RPC receipt separately in bounded metadata: batch completion does not replace the original block receipt or ledger clock. The batch receipt identity binds source owner/version, slot, blockhash, response digests and those transport receipts. No local `now()` supplies event time.

Validate the complete bounded block and every extracted event before selection. Identical repeated event envelopes collapse; contradictory event IDs, signatures or repeated mint identities invalidate the invocation. Distinct successful initializations of the same mint are a conflict, not permission to choose whichever arrived last. Unique tokens are sorted lexically by `(solana, mint)` and truncated to five only after validation; their actual source cursors remain intact for P02-T04/T05/T06. Candidate ID remains the existing `candidate:` plus SHA-256 of canonical JSON `[chain,mint]`. Preserve all actual predecessor identities/digests.

No cursor, continuation or state is carried to another invocation. Coverage gaps are declared, never filled by scanning previous slots. Null/skipped/pruned/unavailable blocks, missing block time, time conflict, unsupported transaction version, incomplete inner recording or malformed identities stop discovery; there is no earlier-slot fallback, resync request, pagination or retry. An entirely valid block with zero qualifying events yields the existing empty-discovery terminal, not a fabricated candidate. Mint initialization is not P03 eligibility; the existing independent safety owner still follows admission.

### Discovery acceptance budgets

| Dimension | Hard maximum / behavior |
| --- | --- |
| Source invocations / slots / blocks | 1 / 1 / 1 |
| Underlying RPC method calls | 3, one per method above; early STOP reduces calls |
| Small RPC response bodies | 8 KiB each for `getSlot` and `getBlockTime` |
| Block response body | 1 MiB, matching the existing Solana response ceiling |
| Aggregate body bytes | 1 MiB + 16 KiB; enforce while reading, with at most a one-byte overflow sentinel per response |
| Per-call deadline / aggregate source deadline | Explicit positive deadline, at most 10 s / 30 s |
| Parsed transactions / total instructions | 2,000 / 8,192, inclusive caps; excess rejects the entire block |
| Extracted raw observations / payload | 64 / 8 KiB each, as in the existing source contract |
| Admitted tokens | 5, lexical after complete validation |
| Retry / pagination / backtracking / background work | 0 / 0 / 0 / 0 |

These are acceptance/read-work limits, not a promise that every production block fits, or a limit on the RPC server's internal computation. A response over any cap is discarded in full; never parse/admit its first five entries. The existing specification's “one discovery source request” means one source invocation; this design explicitly discloses three underlying RPC calls. Existing provider-neutral owners are unchanged. No actual RPC call was made to validate production fit.

Any future decoder must pin discriminator/layout/version, validate program/account ownership, mint ordering and normalized candidate/base orientation, vault mint/authority, fee arithmetic, initialized mint decimals, and supported token extensions. Unsupported extension effects or fees cannot default to zero.

RPC snapshot mechanism, conditional on a proven pool-address set: one finalized `getMultipleAccounts` containing all pool state, vault and mint accounts, followed by exactly one `getBlockTime(context.slot)`. All reserve quantities and fee state used in a calculation must come from the same returned context, not the discovery slot or separate earlier account reads. `minContextSlot` is a lower bound; it does not request a historical snapshot at that exact slot. With 20 pools, state + two vaults + candidate mint + at most 20 quote mints needs at most 81 distinct account keys, below the documented maximum 100. Null accounts, layout mismatch or missing context time reject the candidate set. Base/quote normalization must permute reserves, decimals, prices and provenance together.

**Enumeration blocker:** standard `getProgramAccounts` can filter by program/layout/mint and sort, but its documented contract has no result-count limit or pagination parameter. `dataSlice` limits bytes per account, not matching account count. Two orientation-filtered scans cannot guarantee a maximum 20-pool complete universe or finite scan cardinality. Client byte rejection can bound the reader, but does not establish an admitted bounded canonical enumeration. This audit does not select that scan, invent `limit=20`, accept provider-first-20 ordering, or imply that its response is always too large.

A standard SPL/Token-2022 program-account scan has the same missing server-side cardinality bound; an account context slot is also not a mint-initialization event time. It is not selected for discovery.

A finite DEX-event universe is a possible resolution: pools initialized or referenced in one explicitly bounded ledger event set. It must define the exact supported instructions, pinned account mapping, reference slot/history range and universe coverage. Selecting it changes the meaning of “highest liquidity” to highest among that declared event-scoped pool set. The mint-initialization discovery above does not itself enumerate those pools. A controller decision packet below makes this coverage choice explicit rather than silently claiming a complete token-pool search.

## 5. Required time, numeric and lineage contract (conditional)

The following is a concrete proposed acceptance policy for the next bounded joint owner, not an active amendment to existing owners:

- One explicit aware UTC evaluation/reference T for all candidates. Every source fact must precede its actual receipt and every receipt must be at or before T. Network collection started after a fixed T cannot manufacture acceptable receipts; future binding must supply previously collected facts or explicitly establish the completed collection reference before invoking the existing cycle. No owner silently moves T.
- Source freshness is inclusive age at most `min(caller stale_after, 180 seconds)`; caller freshness must be explicit and positive. No unknown/future age passes. Discovery uses the block event time, reserves use their finalized account snapshot block time, and USD uses its actual source timestamp or conservatively retained source interval. These clocks remain distinct.
- Proposed maximum reserve/price and base/quote price skew is 120 seconds, inclusive. An exact point price must satisfy every relevant absolute time difference. For a 60-second candle `[start,end)`, retain the interval and conservatively require the maximum endpoint distance from reserve time to be at most 120 seconds; age is measured from start, and end must be at or before price receipt and T. Do not relabel close as an exactly timed trade, replace start by receipt, interpolate, forward-fill empty intervals or choose an older candle to evade the rule. Require both sides to use the same explicitly selected closed interval. Missing or mismatched intervals reject the pool.
- OHLCV confidence is `NOT_PROVIDED`; an oracle confidence field cannot be fabricated. Approving candle-close valuation must explicitly accept that evidence/model limitation. An oracle alternative must instead specify feed ID, exact mint/USD mapping, verified account/program, signed positive price/exponent, publish time, verification level and an explicit confidence bound.
- Proposed narrow formula: `L = (Rb / 10^db) * Pb_USD + (Rq / 10^dq) * Pq_USD`, using net reserve integer quantities and exact decimals. Both price predecessors must be valid and time-compatible. Every side, including stable assets, needs an exact mint-bound USD valuation; no implicit `$1` or doubling of the quote reserve. No reserve-ratio inference of base USD is approved here.
- Proposed numeric representation: reserve/fee integers are checked u64, fees cannot exceed vault amounts; decimals are integers 0..18 for this narrow supported scope. Price decimal strings are positive, finite, at most 128 significant digits and absolute exponent at most 100. Parse without binary floats. Compute using exact integer/rational arithmetic, round the final sum down once to six fractional USD digits, then construct `Decimal` from canonical text; no ambient Decimal precision or intermediate rounding. Zero net reserves cannot produce a positive-liquidity default. Equivalent lexical decimal forms canonicalize identically for lineage.
- Retain a versioned immutable predecessor packet: discovery source/event/slot/blockhash/instruction path, P02 predecessor digest, enumeration universe/coverage/digest, pinned DEX program/layout, exact account keys/owners/raw body digests, snapshot slot/time, actual per-call receipts, raw amounts/fees/decimals, both valuation owners/types/asset identities/prices/source timestamps or intervals/receipts/body digests/confidence status, T, freshness/skew/rounding policy and calculation contract version. SHA-256 of canonical UTF-8 sorted-key JSON binds the full packet. Canonical integers/decimals and UTC timestamp text have one representation; no credentials or provider error body enters it.
- Only a validated packet may produce `CanonicalPoolObservation`. Its `observed_at` is the reserve snapshot time, not the composite receipt or creation time; `received_at` is composite completion and retains individual receipts in the referenced packet. `reference_id` binds the full predecessor packet; the existing target digest remains authoritative over the projected fields. Selector order remains descending canonical USD liquidity, then lexical pool address, never provider order.

These requirements permit deterministic offline replay once source bindings are decided. They do not invent missing facts, attach nonexistent confidence, authorize operational access, or count as implementation closure.

## 6. Budgets, failure boundaries and acceptance tests

Current enforced maxima remain one discovery invocation, five admitted candidates, one pool-source invocation per eligible candidate, at most 20 pool observations each and one selected-pool RTI-11 diagnostic per eligible candidate (maximum five). Safety, scoring, Risk Governor, simulation, persistence and readback owners remain unchanged. A source invocation is not a blanket allowance for undisclosed underlying provider calls.

Discovery method/byte/slot limits are specified in §2. The conditional reserve snapshot requires at most two RPC calls per candidate and one snapshot slot; proposed response caps are 1 MiB plus 8 KiB, deadline at most 10 seconds per call. An event-enumeration source needs its own explicit additional budget before implementation. A two-sided CoinGecko valuation option has an upper bound of 40 HTTP calls per candidate / 200 per five-candidate cycle, at most 1 MiB each; this is a disclosed controller option, **not approved spending or an implemented budget**. Existing maximum five RTI-11 diagnostics is separate and cannot be silently counted as those 200 requests. Oracle/read-only alternatives must disclose their exact bounded account/request/byte totals. There is no complete all-provider total while enumeration/valuation are unselected.
