## 1. Repository audit and decision

`backend/api/main.py` mounts only the read-only lifecycle results router, plus `/health` and `/ready`. `backend/api/paper_lifecycle_results.py` exposes digest catalog and digest readback; it exposes no case preparation, run, or write route. `apps/dashboard` contains only `.gitkeep`. The canonical in-memory chain is RTI-11 result → PFX-01 and PFS-01 over the **same exact RTI-11 object** → CIP-01 `REQUEST_PREPARED` containing one exact `P01Osc02Request` → explicitly invoked OCI-01 → OSC-02 → RTI-15/16 and (if materialized) exact `ControlledPaperLifecycleResult`. PFX-01 delegates RTI-12/13/14; PFS owns simulation-only paper inputs. No facade may bypass their validation or duplicate their domain ownership.

`OneShotPaperPersistenceService` (OSP-01) accepts only `P01Osc01Result`; it does not accept OCI/OSC-02. Existing `ControlledPaperPersistenceService.persist(ControlledPaperLifecycleResult)` (RTI-03) owns the atomic write, idempotent already-stored comparison, conflict, invalid input and storage-unavailable outcomes. Its read service and RTI-07 digest catalog own readback. A separate thin OCI/OSC-02-to-RTI-03 application handoff is required before operator persistence can be exposed; it must pass the **exact** lifecycle object and never call OSC again. RTI-03 does not durably retain OCI/CIP/OSC wrappers or complete replay inputs.

**Decision:** B — foundation is ready for design; two backend dependencies are now specified: a controller-selected server-side one-shot RTI-11 diagnostic gated on canonical P02/P03 prerequisite provenance, and separate optional OSC-02 lifecycle-to-RTI-03 composition. Neither is solved by browser-side object reconstruction. Facade implementation must prove the intake path before claiming end-to-end raw-input preparation.

## 3. Exact case identity and temporary state

CIP-01 and OCI-01 require identity (`is`) of nested RTI-11, RTI-14 and PFS objects, and OCI passes CIP's exact `P01Osc02Request` by identity. A digest, signed JSON token or browser-reconstructed dataclass cannot guarantee those Python references across requests. Choose a **process-local, bounded, temporary server case registry** with an opaque unpredictable handle and server-side access control; hold the exact immutable CIP result, OSC request, optional OCI/OSC/lifecycle and RTI-03 results. This is operational control state, not RTI-03 persistence, replay archive, or a new domain owner. Never expose raw canonical objects or secrets in the handle.

An immutable case digest binds CIP contract/version, CIP result digest, OSC invocation ID and input digests, RTI-11/PFX/PFS lineage and preparation outcome. An opaque handle identifies the stored object *instance*; the digest validates contents and optimistic review consistency, not a global reservation. A handle is scoped to the authenticated operator/session where authentication exists; without a defined access-control boundary, do not expose mutation routes on a public deployment. The future implementation must specify allowed process topology (single process or an identity-preserving shared object host), finite capacity/TTL, cleanup and lifecycle of cases and results, and a safe restart/expiry outcome. Do not add network/shared persistence or cross-process object serialization to work around identity.

State machine: `PREPARING → REVIEW_READY | PREPARATION_STOPPED | PREPARATION_UNAVAILABLE`; only `REVIEW_READY → RUN_CLAIMED → RUN_TERMINAL | RUN_OUTCOME_UNKNOWN`; only a canonical lifecycle-bearing `RUN_TERMINAL → PERSIST_CLAIMED → PERSIST_TERMINAL | PERSIST_OUTCOME_UNKNOWN`. Atomic per-case transitions prevent concurrent double submission. Any second run, lost case, expired handle, digest mismatch or uncertain owner call must **not** invoke OCI again; present bounded conflict/unknown and require explicit controller resolution. Do not advertise global exactly-once across processes or after restart. If process fails while the run is in flight, outcome is unknown, not safely retryable. Persist uncertainty may be investigated through RTI-03 digest readback; readback does not justify automatic second persist. A second independently prepared case with the same invocation ID is not a globally reserved duplicate: future global idempotency requires a separate decision.

## 4. Proposed minimum transport contract (future, not implemented)

Version routes under `/api/v1/operator/paper-cases`; request/response DTOs are safe projections, *not* replacements for canonical owner records.

- `POST /paper-cases`: explicit, versioned selected input and trusted evidence references/values. In its authorized intake variant, construct canonical RTI-11 once through the selected bounded diagnostic after trusted P02/P03 validation, PFX/PFS once each against that same object, then CIP once. Return opaque handle, case digest, input summary and `REVIEW_READY` or safe owner STOP. Do not invoke OCI. If evidence is only a claimed client digest with no trusted server object, reject.
- `GET /paper-cases/{handle}`: read review projection, immutable case identity/digests, explicit assumptions, reason codes and current process-local status. A read does not rerun owners.
- `POST /paper-cases/{handle}/run`: explicit review digest/precondition and operator intent; only REVIEW_READY. Claim once, call `PreparedPaperCaseInvocationService.run(P01Oci01Request(exact_cip_result))` once; return safe OCI/OSC terminal projection. No automatic retry/persist.
- `POST /paper-cases/{handle}/persist`: explicit operator intent and matching OCI/OSC/lifecycle digests; only canonical lifecycle-bearing terminal. A separate thin application handoff calls RTI-03 with the exact lifecycle once; preserve STORED, ALREADY_STORED, CONFLICT, INVALID_INPUT and STORAGE_UNAVAILABLE without rewriting. Do not use OSP-01 or RTI-04.
- Existing GET digest catalog and GET digest read remain the only durable read surface; link to these by exact RTI-03 lifecycle digest. No new archive, mutation, execution or evaluation endpoint.

Transport rejects malformed/version/identity/case digest mismatch before owner calls with safe 4xx; canonical ineligible owner outcomes are 200 with explicit STOP status/reasons, not forged success. Missing/expired case is 404/410 as specified at implementation; conflicting or already claimed action is 409; owner availability maps to finite safe 503 or a documented bounded terminal result, retaining exact owner outcome in server memory. Return `Cache-Control: no-store`, request ID, no raw exception text, no sensitive raw evidence or Python exception in errors. Explicit HTTP timeouts do not permit replays. No wall-clock value enters canonical CIP/OSC/PFS material or digests; TTL is only registry control metadata, never paper evidence.

**Cardinality:** a future authenticated and explicitly authorized prepare invokes RTI-11 at most once through its existing one-shot diagnostic path, PFX once, PFS once and CIP once; review zero; run OCI once, whose OSC call is at most once and internal RTI-15/16 remain OSC-owned; persist RTI-03 once per accepted claim; readback one existing query per request. No owner rerun across routes. Failed/terminal preparation performs no run. Future focused tests must prove same-object lineage, state claim races, expiry/restart/unknown handling, owner STOP and invalid response propagation, zero hidden invocations, explicit persist eligibility, RTI-03 idempotency/conflict and digest readback, safe serialization, and no operational provider/live experiment in tests.

## 5. Hunter Room functional foundation

The **Hunter Room is the primary workspace**, with a compact top status rail and progressive case panels, not a sidebar add-on or a “Live AI Pipeline.” On desktop use a broad central case canvas with evidence/review and action/result columns; on iPad portrait stack these sections into a single readable flow with persistent case identity/status and visible review/run controls, no horizontal scrolling or hover-only controls. Keyboard, touch targets, focus, contrast and screen-reader statuses must remain usable. A static responsive shell and a read-only mock of the API projection can precede write-route authorization; its controls stay disabled until the corresponding backend endpoint and operational authorization exist.

| View | Data source and states |
| --- | --- |
| Selection and evidence | Explicit candidate/chain/token/exact pool, observed historical market provenance/freshness, paired safety and eligibility; display missing/unavailable plainly. |
| Review | Canonical opportunity, DecisionIntent, Risk/Capital APPROVED/REJECTED and scope, PFS versioned simulation assumptions, historical proxy label, CIP digest and input digests; require deliberate confirmation. |
| Run result | OCI/OSC/RTI stages, exact bounded outcome/STOP reason, optional RTI-16 paper lifecycle and stage digests; never infer economic success from lifecycle completion. |
| Optional persistence and readback | Separate persist control and RTI-03 status, lifecycle digest, link to existing digest read API; render NOT_FOUND/CORRUPT/STORAGE_UNAVAILABLE distinctly. |
| Future evaluation slot | Explicit “not available” placeholder only; P08 evaluation/learning data and economic measures are not produced here. |

Frontend architecture: typed transport DTO boundary; normalized immutable per-case view models keyed by opaque handle and case digest; finite UI state machine mirroring server states, with server state authoritative after refresh; components for CaseHeader, SelectionInputs, EvidenceReview, DecisionRiskReview, SimulationAssumptions, ExplicitRunControl, TerminalDetails, PersistenceControl, ReadbackView and future ActivityViewport. Activity animation later must consume **actual server stage/status events**, never invented agents or provider progress. Loading and uncertain response states disable action rather than automatically retry; safe errors show bounded reason plus request ID and preserve access to existing terminal record. Display historical PFS close as **simulation-only price proxy**, capacity/friction as assumptions; no executable quote, real liquidity/fill, transaction inclusion, economic P&L or real-time feed.

## 7. Controller amendment — trusted RTI-11 source and operator access

**This section supersedes earlier unresolved sourcing/access choices in §§1–4 and 6. Status remains specification only.** The controller chose one server-side RTI-11 diagnostic per authenticated, explicitly requested prepare. No operational call is authorized in this cycle.

### 7.1 Exact RTI-11 owner and input provenance

`MarketToOpportunityCompositionService.compose(P01Rti11CompositionRequest)` is the existing owner. Its request requires explicit `candidate_id`; canonical `P02T07PredecessorContext` (P02-T06 materializer contract); controller-selected `ExactPoolDiagnosticTarget` (`chain_id`, `token_mint`, `pool_address`, `base_mint`, `quote_mint`, `target_reference_id`, `target_reference_digest`, `target_contract_version`); paired canonical `SafetyEvaluationResult` and `DerivedEligibilityOutput`; `reference_time`; explicit positive `timeout`; `max_response_bytes`; explicit `FreshnessPolicy` with `stale_after`; `processing_time`; `evaluated_at`; and optional explicit `evaluation_id` and bounded `analytical_context`. PFX ruleset/policy seed, PFS selected historical observation and versioned policy, simulation reference/state/replay facts and OSC invocation ID remain explicit under their existing owners. No hidden transport defaults may substitute for operator decisions.

The facade owns decoding/access, trusted object intake and cross-reference linkage only. It cannot assume browser-asserted P02/P03 objects, provider payloads or digest strings prove canonical provenance. Exact-pool target reference digest alone is not trusted pool approval. It must link the controller's candidate, chain/token and exact pool to a canonical current P02 predecessor and paired P03 evaluation/eligibility from existing owners or already-held server-side validated evidence; RTI-11 checks P03 identity, contract/evaluator, timestamps and evidence references. The P02 guard `P02T07PredecessorContext.contains` runs before provider credential access. If a future implementation cannot establish those upstream objects from existing owner outputs or verified underlying evidence, it must reject prepare before RTI-11/provider and return to controller review. This amendment creates no P02/P03 owner, fabricated evidence or browser-authoritative provenance.

An eligible authenticated prepare calls RTI-11 `compose` at most once. RTI-11 calls `run_controlled_ohlcv_diagnostic` once, which calls `run_ohlcv_diagnostic` at most once after the P02 guard. Existing `fetch_pool_ohlcv` performs one GET to the fixed CoinGecko Solana exact-pool minute OHLCV endpoint: minute-floored UTC `reference_time` cutoff, aggregate 1, limit 3, USD currency, selected token and exact pool, redirects disabled, explicit timeout, response cap 1–1,048,576 bytes. The server alone reads `COINGECKO_DEMO_API_KEY`; credentials and headers never enter client output or provenance. Missing/invalid key returns canonical bounded authentication failure without GET. No alternate provider, pool, follow-up GET or retry.

Canonical mapper/price-direction policy owns observation/signal production. `FreshnessPolicy.stale_after`, source close/receipt times, diagnostic evaluation time, cutoff and identity/quality checks remain with canonical owners. The facade supplies explicit paper/reference/evaluation times and does not substitute wall clock into deterministic paper material; existing transport clock produces only the diagnostic's observed receipt/evaluation facts. Preserve source response digest, provider/adapter/version, selected pool, timestamps and RTI-11 digest in the in-memory lineage. An OHLCV historical close is a simulation proxy, never executable quote/liquidity.

Canonical `TOKEN_NOT_CURRENT` or `DIAGNOSTIC_NOT_PRODUCED` stops before PFX/PFS/CIP. Nested outcomes may be AUTHENTICATION_FAILED, RATE_LIMITED, TIMEOUT, SOURCE_UNAVAILABLE, RESPONSE_TOO_LARGE, INVALID_RESPONSE, IDENTITY_MISMATCH or stale evidence; preserve exact owner outcome/reasons and expose finite safe STOP. Malformed/unsupported P02/P03/target/time inputs are validation failures; unexpected owner failure is bounded unavailable without raw exception text. Never retry or repair. The **same RTI-11 object instance** is passed to PFX and PFS and remains linked through CIP; review/run/persist invoke RTI-11 zero times.

### 7.2 Minimal operator authentication and authorization

Relevant FastAPI surface has read-only lifecycle GET and health/readiness. `backend/core/config.py` has environment settings but no operator credential, identity/session provider or role database; `RequestIdMiddleware` is correlation only. No relevant reusable operator authentication/session/CSRF mechanism is present. Select one **server-configured high-entropy bearer credential** for the single-controller operator use case, provisioned outside source control through deployment secrets (proposed name `MCH_OPERATOR_API_TOKEN`). Never commit token or `.env`, send it in URL, log it, or embed it in case handle. Require TLS for public transport, compare supplied `Authorization: Bearer <token>` in constant time, and redact logs/errors. No third-party auth, accounts, refresh tokens or production identity service is introduced.

Authentication verifies this configured single controller; authorization separately grants only the verified operator permission for prepare, run, persist and sensitive case-review GET. Enforce the access check **before** case lookup, intake/provider call, run/persist claim and sensitive response. Opaque case handle is an object locator, never authentication or proof of authority. Missing/invalid bearer → safe 401; authenticated identity without mutation permission → 403; absent/invalid operator-access configuration → safe 503 before owners or case lookup. Never enable open mutation, a hardcoded/default token, debug bypass or permissive public deployment. Existing read-only lifecycle catalog/readback and health/readiness retain their current contracts.

Use Authorization header, **no cookie session** for this milestone. No ambient browser credential means cookie CSRF is inapplicable; a future cookie approach requires a separate CSRF decision. For cross-origin dashboard access, require a configured allowlist of exact origins; never wildcard mutation CORS or credentialed wildcard. Origin is additional browser protection, not authentication because non-browser clients can forge it. Same-origin hosting still requires bearer authentication. Browser token delivery is a deployment prerequisite: keep it out of URL, localStorage and diagnostics, and do not publish operator controls if secure delivery/TLS/configuration is absent. Rotation or process restart cannot make an uncertain run retryable. Existing request ID, no-store and safe-error conventions apply.
