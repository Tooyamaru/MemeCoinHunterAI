## 1. Repository audit and decision

`backend/api/main.py` mounts only the read-only lifecycle results router, plus `/health` and `/ready`. `backend/api/paper_lifecycle_results.py` exposes digest catalog and digest readback; it exposes no case preparation, run, or write route. `apps/dashboard` contains only `.gitkeep`. The canonical in-memory chain is RTI-11 result → PFX-01 and PFS-01 over the **same exact RTI-11 object** → CIP-01 `REQUEST_PREPARED` containing one exact `P01Osc02Request` → explicitly invoked OCI-01 → OSC-02 → RTI-15/16 and (if materialized) exact `ControlledPaperLifecycleResult`. PFX-01 delegates RTI-12/13/14; PFS owns simulation-only paper inputs. No facade may bypass their validation or duplicate their domain ownership.

`OneShotPaperPersistenceService` (OSP-01) accepts only `P01Osc01Result`; it does not accept OCI/OSC-02. Existing `ControlledPaperPersistenceService.persist(ControlledPaperLifecycleResult)` (RTI-03) owns the atomic write, idempotent already-stored comparison, conflict, invalid input and storage-unavailable outcomes. Its read service and RTI-07 digest catalog own readback. A separate thin OCI/OSC-02-to-RTI-03 application handoff is required before operator persistence can be exposed; it must pass the **exact** lifecycle object and never call OSC again. RTI-03 does not durably retain OCI/CIP/OSC wrappers or complete replay inputs.

**Decision:** B — foundation is ready for design; two small backend dependencies remain: an explicit, trusted controlled-input intake that produces the canonical RTI-11 result for a selected candidate/exact pool, and a separate optional OSC-02 lifecycle-to-RTI-03 composition. Neither is solved by browser-side object reconstruction. Facade implementation must prove the intake path before claiming end-to-end raw-input preparation.

**Intake prerequisite:** RTI-11's current composition owns controlled OHLCV diagnostic invocation, including an explicit one-shot external transport, and requires a canonical paired P03 safety evaluation/eligibility input. This specification does not license live/provider calls or assume arbitrary JSON can be converted into an already-produced canonical RTI-11 object. The future facade contract must choose and validate a *trusted server-side* production mechanism for RTI-11 and explicit paired safety evidence (one authorized bounded diagnostic call if separately approved, or exact already-held server canonical result); until that contract exists, the operator-facing raw-input prepare route is unavailable. The browser sends explicit input values and selection, never serialized internal Python object graphs or claimed digest-only objects. The trusted server constructs canonical objects once and retains their references. If no legitimate bounded RTI-11 source is available at implementation review, STOP on this dependency rather than fabricate observations or silently call a provider.

## 3. Exact case identity and temporary state

CIP-01 and OCI-01 require identity (`is`) of nested RTI-11, RTI-14 and PFS objects, and OCI passes CIP's exact `P01Osc02Request` by identity. A digest, signed JSON token or browser-reconstructed dataclass cannot guarantee those Python references across requests. Choose a **process-local, bounded, temporary server case registry** with an opaque unpredictable handle and server-side access control; hold the exact immutable CIP result, OSC request, optional OCI/OSC/lifecycle and RTI-03 results. This is operational control state, not RTI-03 persistence, replay archive, or a new domain owner. Never expose raw canonical objects or secrets in the handle.

An immutable case digest binds CIP contract/version, CIP result digest, OSC invocation ID and input digests, RTI-11/PFX/PFS lineage and preparation outcome. An opaque handle identifies the stored object *instance*; the digest validates contents and optimistic review consistency, not a global reservation. A handle is scoped to the authenticated operator/session where authentication exists; without a defined access-control boundary, do not expose mutation routes on a public deployment. The future implementation must specify allowed process topology (single process or an identity-preserving shared object host), finite capacity/TTL, cleanup and lifecycle of cases and results, and a safe restart/expiry outcome. Do not add network/shared persistence or cross-process object serialization to work around identity.

State machine: `PREPARING → REVIEW_READY | PREPARATION_STOPPED | PREPARATION_UNAVAILABLE`; only `REVIEW_READY → RUN_CLAIMED → RUN_TERMINAL | RUN_OUTCOME_UNKNOWN`; only a canonical lifecycle-bearing `RUN_TERMINAL → PERSIST_CLAIMED → PERSIST_TERMINAL | PERSIST_OUTCOME_UNKNOWN`. Atomic per-case transitions prevent concurrent double submission. Any second run, lost case, expired handle, digest mismatch or uncertain owner call must **not** invoke OCI again; present bounded conflict/unknown and require explicit controller resolution. Do not advertise global exactly-once across processes or after restart. If process fails while the run is in flight, outcome is unknown, not safely retryable. Persist uncertainty may be investigated through RTI-03 digest readback; readback does not justify automatic second persist. A second independently prepared case with the same invocation ID is not a globally reserved duplicate: future global idempotency requires a separate decision.

## 4. Proposed minimum transport contract (future, not implemented)

Version routes under `/api/v1/operator/paper-cases`; request/response DTOs are safe projections, *not* replacements for canonical owner records.

- `POST /paper-cases`: explicit, versioned selected input and trusted evidence references/values. In its authorized intake variant, construct canonical RTI-11 once, PFX/PFS once each against that same object, then CIP once. Return opaque handle, case digest, input summary and `REVIEW_READY` or safe owner STOP. Do not invoke OCI. If evidence is only a claimed client digest with no trusted server object, reject.
- `GET /paper-cases/{handle}`: read review projection, immutable case identity/digests, explicit assumptions, reason codes and current process-local status. A read does not rerun owners.
- `POST /paper-cases/{handle}/run`: explicit review digest/precondition and operator intent; only REVIEW_READY. Claim once, call `PreparedPaperCaseInvocationService.run(P01Oci01Request(exact_cip_result))` once; return safe OCI/OSC terminal projection. No automatic retry/persist.
- `POST /paper-cases/{handle}/persist`: explicit operator intent and matching OCI/OSC/lifecycle digests; only canonical lifecycle-bearing terminal. A separate thin application handoff calls RTI-03 with the exact lifecycle once; preserve STORED, ALREADY_STORED, CONFLICT, INVALID_INPUT and STORAGE_UNAVAILABLE without rewriting. Do not use OSP-01 or RTI-04.
- Existing GET digest catalog and GET digest read remain the only durable read surface; link to these by exact RTI-03 lifecycle digest. No new archive, mutation, execution or evaluation endpoint.

Transport rejects malformed/version/identity/case digest mismatch before owner calls with safe 4xx; canonical ineligible owner outcomes are 200 with explicit STOP status/reasons, not forged success. Missing/expired case is 404/410 as specified at implementation; conflicting or already claimed action is 409; owner availability maps to finite safe 503 or a documented bounded terminal result, retaining exact owner outcome in server memory. Return `Cache-Control: no-store`, request ID, no raw exception text, no sensitive raw evidence or Python exception in errors. Explicit HTTP timeouts do not permit replays. No wall-clock value enters canonical CIP/OSC/PFS material or digests; TTL is only registry control metadata, never paper evidence.

**Cardinality:** prepare invokes RTI-11 at most once *only if a separately authorized intake permits it*, PFX once, PFS once and CIP once; review zero; run OCI once, whose OSC call is at most once and internal RTI-15/16 remain OSC-owned; persist RTI-03 once per accepted claim; readback one existing query per request. No owner rerun across routes. Failed/terminal preparation performs no run. Future focused tests must prove same-object lineage, state claim races, expiry/restart/unknown handling, owner STOP and invalid response propagation, zero hidden invocations, explicit persist eligibility, RTI-03 idempotency/conflict and digest readback, safe serialization, and no operational provider/live experiment in tests.

## 5. Hunter Room functional foundation

The **Hunter Room is the primary workspace**, with a compact top status rail and progressive case panels, not a sidebar add-on or a “Live AI Pipeline.” On desktop use a broad central case canvas with evidence/review and action/result columns; on iPad portrait stack these sections into a single readable flow with persistent case identity/status and visible review/run controls, no horizontal scrolling or hover-only controls. Keyboard, touch targets, focus, contrast and screen-reader statuses must remain usable. A static responsive shell and a read-only mock of the API projection can precede write-route authorization; its controls stay disabled until the corresponding backend endpoint and operational authorization exist.

| View | Data source and states |
| --- | --- |
| Selection and evidence | Explicit candidate/chain/token/exact pool, observed historical market provenance/freshness, paired safety and eligibility; display missing/unavailable plainly. |
| Review | Canonical opportunity, DecisionIntent, Risk/Capital APPROVED/REJECTED and scope, PFS versioned simulation assumptions, historical proxy label, CIP digest and input digests; require deliberate confirmation. |
| Run result | OCI/OSC/RTI stages, exact bounded outcome/STOP reason, optional RTI-16 paper lifecycle and stage digests; never infer economic success from lifecycle completion. |
| Optional persistence and readback | Separate persist control and RTI-03 status, lifecycle digest, link to existing digest read API; render NOT_FOUND/CORRUPT/STORAGE_UNAVAILABLE distinctly. |
| Future evaluation slot | Explicit “not available” placeholder only; P08 evaluation/learning data and economic measures are not produced here. |

Frontend architecture: typed transport DTO boundary; normalized immutable per-case view models keyed by opaque handle and case digest; finite UI state machine mirroring server states, with server state authoritative after refresh; components for CaseHeader, SelectionInputs, EvidenceReview, DecisionRiskReview, SimulationAssumptions, ExplicitRunControl, TerminalDetails, PersistenceControl, ReadbackView and future ActivityViewport. Activity animation later must consume **actual server stage/status events**, never invented agents or provider progress. Loading and uncertain response states disable action rather than automatically retry; safe errors show bounded reason plus request ID and preserve access to existing terminal record. Display historical PFS close as **simulation-only price proxy**, capacity/friction as assumptions; no executable quote, real liquidity/fill, transaction inclusion, economic P&L or real-time feed.

## 6. Implementation milestone separation and governance

**Recommendation: two sequential bounded implementation gates.** `P01-OAF-01` first specifies/implements trusted controlled-input intake, identity-preserving temporary registry, read/review/run facade and *separate* OSC-02-to-RTI-03 persistence handoff with focused race/failure tests. Its activation of operational paper invocation requires an explicit controller authorization distinct from this architecture checkpoint. `HR-FND-01` follows stable transport schemas with a responsive functional Hunter Room; a static shell/contract fixtures may be developed in parallel but must not expose live run/persist controls until approved backend is deployed. Separate gates reduce API identity and authority risk; a single merged implementation milestone would obscure whether the backend can preserve exact object identity and safely prevent duplicate operator actions. Advanced visual/animation art is a third optional milestone and cannot invent activity.

P08 evaluation wiring may follow in parallel after foundation; it is not a prerequisite and is not in either gate. No scheduler, worker, queue, provider polling, autonomous discovery/selection, retry loop, wallet/signing/RPC/DEX, transaction, economic realization or live trading. No new persistence schema, full replay archive or RTI-04 shortcut. G2 stays **BLOCKED / UNRESOLVED / NOT AUTHORIZED**; G3/G4/P09 remain **NOT AUTHORIZED**.

**STOP:** Architecture/specification only. No facade, dashboard, API route, registry, operational paper invocation, migration or persistence code is authorized here. Controller review is required to authorize each bounded implementation and resolve controlled RTI-11 intake plus operational exposure/authentication before any write route is enabled.
